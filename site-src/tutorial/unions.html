Declaring unions

While a record stores all of the values declared in it, a union will store only one of the choices available.
These choices are called the case types of the union.
This is useful for a value that can have one of several non-overlapping states.

main void() a u = 1 to b u = "foo" to info log "a {a.nat64 ?? 0}" info log "a {a.string ?? "not a string"}" info log "b {b.string ?? "not a string"}" u union(nat, string)

In this example, declaring u generates functions with these signatures:

  • to u(a nat)
  • nat64 nat?(a u)
  • to u(a string)
  • string string?(a u)

(The function name uses the type's original name, not the alias name. So the name here is nat64 not nat.)

As you can see above, you can put a value of any of the case types into the union unconditionally, but you can only get it out as an option, since the union may have had some other type in it.

Unions do not introduce subtyping; explicit conversion from the case type to the union type is required.
So, it's necessary to write 1 to instead of just 1.

Match expressions

main void() a u = 1 to info log match a as nat x "nat {x}" as void "void" u union(nat, void)

The match expression handles each case type in a separate branch.
Like an if expression, each branch is an expression with the same type as the whole match.
Since log expects a string, each branch of the match is a string too.

Syntactically, the expression extends from the match keyword, to the end of the last branch.
So in this example, it covers the rest of the function after log.

Each branch is parsed as as, then a type name, then a local name (or _), then an indented body. E.g, as nat x introduces a local variable x.
If the branch's type is an empty type (such as void), the local name can be omitted.
Otherwise you must explicitly ignore the local, as in as nat _.

Usually, a match needs an explicit else branch.
The exception is a match on a union value if every case type is explicitly handled in the match.
There is no implicit () like there is for an if. The reason is that match expressions are usually intended to handle every case, so forgetting one should be a compile error.
Here's what that looks like. Try removing the 'else' branch to see the compile error.

main void() info log match "".to::u as nat x "nat {x}" else "something else" u union(nat, string)

Matching on other values

You can also match on other types:

  • symbol or string.
  • Integral types: nat8, nat16, nat32, nat64, int8, int16, int32, int64.
main void() info log ("chocolate" order 1) info log ("pizza" order 2) order string(a string, count nat) plural = a plural count if c ?= a condiment "{plural} with {c}" else plural condiment string?(a string) match a as chocolate "peanut butter", as "french fries" "ketchup", else () plural string(a string, count nat) match count as 0 "no {a}s" as 1 "one {a}" else "{count} {a}s"
as chocolate is the same as as "chocolate".
Quotes are not required if it is a valid identifier.

A more complex example

A typical pattern is to declare a union of several record types that are declared along with it.

main void() shoes = 10 unsold info log "Shoes for $9? {shoes can-sell 9}" info log "Shoes for $10? {shoes can-sell 10}" ring = 50 has-bid info log "Ring for $50? {ring can-sell 50}" info log "Ring for $51? {ring can-sell 51}" info log "Sales so far: ${(shoes, ring) expected-sales}" item union(unappraised, unsold, has-bid) unappraised record unsold record(min-price nat) has-bid record(actual-price nat) can-sell bool(item item, offer nat) match item as unappraised false as unsold x offer >= x.min-price as has-bid x offer > x.actual-price expected-sales nat(items item[]) res mut nat = 0 for item : items if bid ?= item has-bid res +:= bid actual-price res

Empty types

unappraised record declares an empty type. This takes up no space and is distinct from other empty types.
In a match, it isn't required to have a destructuring. You can write as unappraised instead of as unappraised x.

Creating union values from records

As usual, the record types each have a constructor named new.
For convenience, declaring a union case type that is a record generates a function with the record name and the same signature as the record constructor, but returning the union type instead.
For example, one of these has the signature unsold item(min-price nat).
So, 10 unsold could have been written as (10,)::unsold to.
Union case types don't have to be records, but only records will get these named constructors.

Methods

If a function exists for every case type, you can declare it on the union.

main void() a u = 1 to info log "{a}" u union(nat, string) show string()

The method is show string(). The first (and in thie case only) parameter is implicit.
The method generates a function show string(a u). To implement this function, Crow looks for show string(a nat) and show string(a string). The method calls the appropriate implementation based on the union's actual value using a (hidden) match.

Here's an example with more parameters on the method:

main void() a u = 10 unsold info log "{a can-sell 10}" u union(unappraised, unsold) can-sell bool(offer nat) unappraised record unsold record(price nat) can-sell bool(_ unappraised, _ nat) false can-sell bool(a unsold, offer nat) offer >= a.price
The method implementations are just regular functions.
They don't need anything to mark them as method implementations, they are in the searched for in the case's scope based on the method's signature.

For a union type, methods are just a convenience that saves you from writing a match manually.
We'll soon see that they are indispensable for variant and interface types.
